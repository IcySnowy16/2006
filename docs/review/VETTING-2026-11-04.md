## Recommended, not built

### C-004: forgot password, so e-mail ownership wins

The standard fix is to make proof of the inbox the thing that sets the password:

1. `POST /api/auth/password-reset { ntuEmail }` sends a 6-digit code. Reuse `issueCode`, the HMAC, the 10-minute TTL, 3 attempts and the `resend` rate limit. Always answer 204, so it doesn't reveal whether the address exists.
2. `POST /api/auth/password-reset/confirm { ntuEmail, code, newPassword }` sets the new hash, marks the account ACTIVE if it was pending, and bumps `sessionVersion` so every old session ends.
3. A "Forgot password?" link on Sign in.

This also fixes the squatter case: the owner resets the password from their inbox. Don't "let a new sign-up overwrite an unverified
one", because a squatter can then overwrite the owner's sign-up just before the owner verifies.

### Idempotency on the client

Disable "Share my location and go live" while the request is pending. For money moves (top-up, booking), send an `Idempotency-Key`
header, the Stripe pattern, so a retry on flaky campus Wi-Fi can't happen twice.

### A3: passwords

Follow NIST SP 800-63B: keep the 8-character minimum, add a small blocklist (`password1`, `12345678` and so on), and add no
composition rules. A strength bar is optional.
