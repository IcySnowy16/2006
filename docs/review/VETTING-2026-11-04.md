### Google Maps advice

- **Correct:** Directions API has been Legacy since 1 Mar 2025, and new Cloud projects can't enable it. So the draft's `GoogleMapsAdapter` (`.../maps/api/directions/json`) fails with a key made on a new project, and works without a key through the fake. Using Routes and Geocoding on the server key, and Maps JS on a browser key restricted to `http://localhost:5173/*`, is the right setup.
- **Add:** the draft has **no** browser-key code at all (`VITE_GOOGLE_MAPS_BROWSER_KEY` appears nowhere), so the browser key only matters on Staging.
- **Stronger than they said:** the URL signing secret was pasted into chat. Regenerate it, don't just "can". It costs nothing.

## Fixes on this branch

1. **G5: one active journey per driver, enforced by the database.**
   `server/prisma/migrations/20261104000000_one_active_journey`: a partial unique index on `Journey(driverId)` WHERE status is LIVE, OPEN, FULL or IN_PROGRESS.
   `JourneyService.goLive` turns the unique violation into the usual 409 `ILLEGAL_STATE_TRANSITION`. The test makes 3 parallel calls and gets 201, 409, 409.
   _Why this and not a lock in code:_ it also covers the geofence job, seeds and any future code path, and it costs nothing at runtime. This is the same "make the database the referee" approach the repo already uses for ratings (`P2002` gives `ALREADY_RATED`).
2. **X1: role choice follows the trip.** `RoleService.setActiveRole` now refuses a switch only when the current trip is in the **other** role. Choosing the trip's own role (for example DRIVER while live) always works, even from no role. Switching to PASSENGER while live is still refused (tested).

## Recommended, not done (needs a team decision)

### F2: lock the fare the rider agreed to (how Grab and Uber do it)

Grab advertises shared fares as _fixed and shown upfront_. In Malaysia, when a GrabShare co-rider cancels, the other rider's booking simply proceeds, and the canceller pays a fee that compensates the driver. UberX Share applies the discount upfront _whether or not_ a co-rider is matched. Neither one charges the remaining rider more after the fact, and neither one puts that rider into debt.

Smallest change that matches this, in `TripService.complete`:

```ts
// never charge more than the rider agreed to (their hold at confirmation)
const charge = Math.min(fare!, b.currentFareCents);
```

Also stop `FareService.retier` from **raising** holds; lowering them is still fine. The $1 difference is either absorbed by the driver (it's simulated money) or covered by a no-show/cancel fee on the rider who caused it, as Grab does. Either way, FR 5.1.3 needs a one-line SRS change. The F2 test is ready: remove `.fails` once you decide.

### T5 and T6: let the server say which buttons to show

Today the client guesses from `status`, `pickupStatus` and the socket state. That's why Cancel appears when the server will refuse it. Ride-hailing apps drive the screen from the server's state machine. Suggestion: add `allowedActions: ('CANCEL'|'RATE'|'CALL')[]` to the booking response, computed from the same entity methods the server already uses (`Booking.cancel()`), and render the buttons from that. Also add a `pickupStatus === 'NO_SHOW'` banner on `BookingPage`.

### G6: say when the scheduled journey starts

Grab's Advance Booking always shows "Scheduled for 08:00". On Go Live, when `departureTime > now`, show "Riders see you now; trip departs 08:00".

### G5, part 2: idempotency on the client

Disable "Share my location and go live" while the request is pending. For anything that moves money (top-up, booking), send an `Idempotency-Key` header, the Stripe pattern, so a retry on a flaky campus network can't double-charge.

### A3: passwords

If you change anything, follow NIST SP 800-63B: keep the 8-character minimum, add a small blocklist of common passwords (`password1`, `12345678` and so on), and don't add composition rules. A strength bar (zxcvbn-ts) is optional polish, not a requirement.
